Genesis · production deployment

How a commit becomes production

A merge to main deploys itself — but only after CI has gone green on that exact commit. Nothing in the pipeline holds a credential except the one key that lets it ask Secret Manager for the rest.

What starts a deploy

The deploy is chained to CI's completion, not to the push. That is the whole reason it can be trusted to run unattended: a push trigger would race CI and could put an untested commit in front of users, whereas workflow_run waits for the verdict and reads head_sha — so it deploys the commit that was actually tested, not whatever main points at by the time a runner frees up.

The fifteen steps

Ordered so that anything cheap enough to fail fast does. The two highlighted steps are the ones that decide whether the run means anything: the deploy itself, and the check that the thing it deployed actually answers.

  1. 01 Resolve the commit to deploy CI's head_sha, or the ref you typed, or main.
  2. 02 actions/checkout At that exact SHA — not at the branch head.
  3. 03 actions/setup-node Node 22, with all three lockfiles cached.
  4. 04 Install npm ci three times — root, frontend, functions. Never install: ci fails if a lockfile disagrees with its package.json.
  5. 05 google-github-actions/auth Writes the service-account key to a file and exports GOOGLE_APPLICATION_CREDENTIALS. It runs before the build, because the build's configuration comes from Secret Manager and this is what unlocks it.
  6. 06 setup-gcloud So the next step can read a secret.
  7. 07 Resolve the project from the repository Project id from .firebaserc, Firestore database id from firebase.json. Both are committed, so a copy in GitHub would be a second source of truth for a value that already has one.
  8. 08 Fetch the SPA configuration The FRONTEND_ENV secret, straight from Secret Manager to frontend/.env — never through a shell variable or an env: block. It prints the key names and a count, never the values.
  9. 09 Write functions/.env One line, the database id from step 07. Everything else the functions need is a defineSecret.
  10. 10 Build the SPA vue-tsc then vite build.
  11. 11 No Firestore SDK in the bundle Scans the built artefact. It is the only layer that can catch a transitive pull of the client SDK — the ESLint rule and the source scan both read our own code, so neither would notice a dependency importing it on our behalf.
  12. 12 Resolve deploy targets Everything, or just one surface if you chose one.
  13. 13 Deploy Functions, Hosting, Firestore rules and indexes. --force, so a function deleted from source is deleted from the project: source is the only thing that decides what exists.
  14. 14 Smoke test the deployed API See below — this is the step that turns "it uploaded" into "it works".
  15. 15 Summary Commit, targets, project and site into the run summary. Runs even when something above failed.

Why the smoke test earns its place. A deploy that reports success has proven the upload and nothing else. /api/health writes a Firestore document, reads it back and deletes it — so a 200 proves four separate things at once: the Hosting rewrite reaches the function, the function booted, its configuration arrived, and the Admin SDK can reach the named database. Each of those has broken a deploy before, and none of them shows up as a failed upload.

Where the secrets come from

Two lanes, and the difference between them is the point. Values the functions read never leave Google's side: the deploy attaches a reference, and the Cloud Run instance resolves it as it starts. Values the browser needs cannot be secret at all — Vite compiles them into the bundle, so they end up served to every visitor no matter where they were stored.

Secret Manager entry Bound to What it is
ANTHROPIC_API_KEY generate The model key. One function only — the one that spends money.
HL_CLIENT_SECRET api Half the marketplace app's credentials. HighLevel shows it once, at creation.
OAUTH_STATE_SECRET api The key every OAuth state is sealed under. Read it and the uid a callback carries becomes forgeable.
HL_CLIENT_ID api Configuration, not a credential — here so no step has to write a .env.
HL_REDIRECT_URI api Must match the marketplace registration byte for byte.
ALLOWED_ORIGINS api + generate Both, because generate.ts imports the allowlist from api. Bound to one alone, the other falls back to localhost and rejects the real site.
FRONTEND_ENV the build The SPA's whole .env as one entry, because the deploy writes it back out as one file.

Adding or rotating one

# A credential — you type the value, it never passes through a script
npx firebase functions:secrets:set ANTHROPIC_API_KEY --project hl-genesis-app

# Configuration — read from your local .env, pushed as a new version
scripts/setup-deploy.sh

# Either way, a running instance keeps the old value until it is replaced
gh workflow run deploy.yml -f targets=functions

A new version is not a deploy. Cloud Run resolves a secret when an instance starts, so adding a version changes nothing for instances already running. Rotating means adding the version and redeploying — which is why the third command is there and not an afterthought.

What has actually gone wrong

Three real failures from building this, kept because each one misdirects — the message names something other than the cause.

parse The workflow never ran, and nothing said why

A comment inside a run: block contained a literal empty expression — ${{ }}. GitHub parses expressions inside run: regardless of comments, so the file was invalid and the workflow simply did not exist. Every test suite stayed green throughout; the Actions tab listed the workflow by its file path instead of its name, which is the only visible tell.

Now caught by: actionlint, running first in CI. A workflow is not compiled, not typechecked and not imported by any test — it is parsed at trigger time, so nothing else can see a mistake in one.

billing "Cloud Billing API has not been used in this project"

Nothing was wrong with the billing account. firebase-tools checks the plan before deploying a v2 function, because those require Blaze, and that check needs cloudbilling.googleapis.com — which had never been enabled. The failure arrives late, after rules and indexes are already applied, and the word "billing" sends you to the wrong console page.

Now caught by: setup-deploy.sh, which enables the eleven APIs a deploy needs.

silent The model key was missing and nothing complained

The Secret Manager API had never been enabled on the project, so ANTHROPIC_API_KEY did not exist — and a function whose declared secret cannot be resolved deploys perfectly happily. It answers 500 on the first real generation and says nothing before that.

Now caught by: requiredSecret(), which throws a message naming the secret instead of letting an empty string reach the SDK — and by index.spec.ts, which asserts every binding structurally, because under the emulator a secret resolves from process.env whether it was granted or not.

Sources of truth: .github/workflows/deploy.yml, scripts/setup-deploy.sh, functions/src/index.ts. Anything on this page that disagrees with those is out of date.
