Slice 08 · design companion

The permit desk

Genesis holds a token that can read an entire business's CRM, and it is about to let generated code use it. Everything in this slice is one question asked four ways: what, exactly, is allowed through the counter?

F7.1 · F7.2 · F8.3 · F1.3 depends on slice 2 48 acceptance criteria the contract is 02-prd.md

This page draws what the PRD can only describe. The acceptance criteria, the decisions and the test matrix live in 02-prd.md, which is the document the build is graded against; nothing here restates them. What is here is the shape of the boundary, the order of one call through it, the reason the upstream URL cannot be tampered with, and the single concurrency hazard the slice exists to get right.

01 · the boundary

What crosses the counter, and what never does

Three zones, two crossings. The caller is a browser — today the dashboard, from Slice 10 a sandboxed iframe's host — and it is never trusted with a credential. HighLevel is a third party that will happily answer anyone holding a bearer token. Between them sits one Cloud Function route which is the only thing in the system that has ever seen both.

The four items on the dashed line are the ones that make this slice a security slice rather than a plumbing slice. None of them is supplied by the caller, and three of them are discarded if the caller supplies them anyway.

02 · the sequence

One call, eleven steps, eight ways out

The order matters more than the steps do. Every refusal that can be decided from the request alone is decided before anything is read from Firestore, and every refusal that can be decided from our own stored state is decided before HighLevel is contacted — so a request that is going to be refused costs nothing, and a request that reaches HighLevel has already been proven to be one this user may make.

03 · the structural claim

The upstream URL is a template, not a string

Every proxy that has ever leaked was, at bottom, a proxy that built a URL by joining something a caller wrote onto something it trusted. The defence usually offered is filtering: reject .., reject %2F, reject a scheme, reject an @. That is a blocklist over URL parsing, and blocklists over URL parsing have a poor record.

The alternative below is not a better filter. It is an assembly step in which the caller's path is consumed rather than carried: it selects a row and populates parameters, and then it is discarded. What is sent upstream is built from a string literal in our source plus values that have been proven to match [A-Za-z0-9_-]{1,64}.

04 · the hazard

Three calls, one expired token

The preview will fire several proxy calls on first render, and they will all find the same token in the same state at the same moment. HighLevel rotates a refresh token when it is used. So the question is not whether concurrent refreshes happen — they do, by construction — but what the system looks like afterwards.

Two things make the answer boring, and both are worth naming because the naive reading of "network call inside a transaction" is alarming. Firestore's read-write transactions are pessimistic: the second caller's read blocks on the first caller's lock rather than racing it. And the transaction body re-reads before it refreshes, so a caller that was waiting finds the winner's fresh token and returns it untouched.

Why not a lease? Claiming a refreshLeaseUntil field in one transaction, calling HighLevel outside it, and writing the result in a second is the correct answer for a system with real concurrency — and it introduces a lock with an expiry policy, a stale-lease sweep, and a third failure mode. Measured against a hazard that has been shown to be survivable, on a five-day clock, that is machinery bought with the wrong currency. The decision is D23 and it names this alternative so a reviewer can disagree with it on the record.

06 · the failure fan

Every exit, and the sentence at the end of it

F8.3 asks for failed HighLevel calls to be surfaced clearly. "Clearly" is only testable if every upstream condition has a code the preview can branch on and a sentence a person can act on, so both are fixed here rather than improvised at the component. Upstream-originated failures also carry detail — HighLevel's own message about the request, truncated to 200 characters — which is what makes a wrong filter grammar debuggable instead of a shrug.

The one status that is deliberately not mirrored. HighLevel's 401 becomes our 409, never our 401. apiClient is shared by every screen in the app and reads a 401 as "your Firebase session died"; mirroring the upstream status would sign a user out of Genesis because a token in somebody else's system had been revoked. The 409 says what is actually true: there is a conflict between the connection we hold and the one HighLevel will honour, and reconnecting resolves it.

07 · where the risk is

Read the slice off its test levels

How a slice's criteria distribute across the five levels is a design statement, not an accounting one. This slice's mass sits at L1 and L4 in almost equal parts, and that is the shape it should have: the matcher and the error mapper are pure decisions that deserve to be proven without an emulator, while tenant isolation and the refresh race are only real when a real transaction and two real users are involved. The single L5 case is the demo line, as always.

08 · what is still uncertain

The risks worth carrying forward

#RiskWhat holds it
R1 A mistake here leaks another tenant's CRM. The proxy holds a token that reads an entire business's contacts. Three independent structural properties, not one check: uid from the token only, locationId from that uid's own document, URL from a compile-time template. AC-11 makes isolation observable rather than asserted.
R2 A refresh network call inside a retryable transaction. The naive reading spends a refresh token twice. Pessimistic locking, a re-read short-circuit, and a measured grace window behind both. AC-26 asserts the one-refresh property rather than assuming it.
R3 The allowlist is the only thing between generated code and a delete loop. A subtly greedy matcher reopens the API. Over-permissiveness is hard to express: parameters cannot hold a slash by grammar, and assembly cannot hold anything but the template and those parameters.
R4 Two rows have the same shape. Ordering bugs pass every test written from the table's own order. Specificity is order-independent, and the test runs against a reversed table.
R5 One row sends a real SMS. It costs money and reaches a person. Flagged off everywhere but one integration case; out of the Loom.
R6 Two HighLevel shapes are only ⚠️-verified — the contacts filter DSL and the conversations query parameters. A stub built from our own fixtures proves the proxy, not the integration. Query and body are forwarded opaquely, so a wrong grammar is an upstream 4xx with a detail attached rather than a Genesis bug — and Slice 9 owns getting it right. A manual curl per surface against the real sandbox is in the definition of done.
R7 Nothing limits how often a generated app calls the proxy, against a 100-request / 10-second burst ceiling. Bounded and named rather than solved: 429 mapped with upstream's text, X-RateLimit-Remaining forwarded and logged, the real fix (a system-prompt instruction against N+1) is Slice 9's, a per-user quota is stretch S4.
R8 App Check on the proxy is a constraint Slice 10 inherits, and Slice 10 is already the hardest unknown in the build. Recorded now, with the opaque-origin problem beside it and a recommended shape — a parent-side postMessage bridge, so no credential enters the sandbox and the request stays same-origin. Slice 10 still owns the decision; it does not have to rediscover the constraints.
R9 Scope creep is easy to justify here: the plan's own demo for this slice is a curl, which is not a screen. One section on an existing panel, one button, one line per surface. No new component, no new route, no new store, no new dependency. Everything larger is an out-of-scope row with a slice number against it.
