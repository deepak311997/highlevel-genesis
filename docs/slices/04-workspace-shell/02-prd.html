Two writes,

The workspace is three panels and a chat that remembers. Only one of those is hard. A turn is two documents committed together — and a batch gives every serverTimestamp() in it the same reading, so the reply and the prompt it answers are exactly tied on every single turn. This page draws the three things the markdown can only describe: who is allowed to author a message, what the tie does if nothing breaks it, and where a failed send lands.

01

Who is allowed to author a message

The browser sends one field. Everything else about a message — its role, its position, its clock reading — is assigned by the server, and a body that tries to supply any of them is refused rather than quietly stripped.

Today the assistant is an echo, so this looks like fussiness. From Slice 5 on the transcript is the LLM's context: a client that can author an assistant turn can write its own future prompt — one that also carries the HighLevel API cheat-sheet and the user's project files. That is why role is not in the request body, and why the collection is closed even to its owner.

  • supplied by the browser
  • assigned by the server
  • stored in Firestore
  • refused

02

The hazard: one commit, one clock reading

A Firestore WriteBatch resolves every serverTimestamp() sentinel in it to the commit's single timestamp. The prompt and its reply are therefore not nearly tied. They are exactly tied, every time.

Firestore then breaks the tie the only way it can: by document name. A document name here is a random auto-id, so the transcript renders in coin-flip order — the echo above the prompt about half the time. It would present as a flaky test and be a deterministic bug.

Rejected, and it was tempting

One turn document holding prompt and reply together dissolves the tie completely — one document, one timestamp, nothing to break. It fails in Slice 5, where the reply is written separately from a stream and a turn can end in an error with no reply at all. A per-project counter in a transaction is also exactly correct, and buys a contended counter and a transaction on every turn, forever, to order a collection that only ever appends.

And the index nobody can test

Two order keys make this a composite query, and the Firestore emulator serves any query without an index — so L3, L4 and L5 all pass against a project that has none. It fails in production, on the first workspace load after deploy. The mitigation is a line in firestore.indexes.json and a line in the definition of done; there is no test to write. Slice 3 hit the same thing, which is why it is called out twice.

03

Sending a message, end to end

Ten steps from a keypress to a scrolled transcript. The two worth noticing are 8 — where both documents commit together, so a prompt can never be stranded without a reply — and 10, where the store appends the response instead of re-reading the history.

04

Where a failed send lands

One entry, eight exits. Every one of them leaves the draft in the composer and appends nothing to the transcript, so re-submitting is always a legitimate retry.

05

Three panels, and what survives the switch

At 1024px and wider, three resizable panels. Below it, one panel at a time behind a tab list. Those are two different component trees, and crossing the breakpoint unmounts one and mounts the other — which is why the draft does not live in the composer.

This contract changes in Slice 5, and knowingly

The assistant write moves to the stream's done handler and the response becomes the user message alone. The user-message write stays exactly where it is, and the frontend does not change at all — appending the response is already what a streamed reply needs. Written down here so the change reads as planned rather than as churn.

07

Where the risk is tested

Thirty-six rows in the test matrix across thirty-seven acceptance criteria. The shape is a statement about where this slice can go wrong: the boundary is the risk, so L4 carries the most weight — every refusal is asserted over the wire, with the collection checked afterwards rather than only the status code.

L1 · unit 10
L2 · component 9
L3 · rules 2
L4 · integration 14
L5 · end to end 1

The two L3 rows are small and are not optional: rules do not cascade into subcollections, so neither the users/{uid} block nor the projects block says anything about messages. Every case is an assertFails, including the verified owner — the one people skip.

The single L5 is the demo line and nothing more: dashboard → project → send → echo → reload → still there. One per slice, by the plan's own rule.

08

Risks carried into the build

#RiskMitigation
R1 The batch timestamp tie renders the echo above the prompt — on every turn, resolved by a random auto-id. seq, asserted twice: L1 over a synthetic tied pair, and L4 over a real pair written through the route and read back. The L4 one is the assertion that matters, because it exercises the actual commit.
R2 The composite index is missing in production and no test can see it — the emulator serves any query. Declared in the same commit as the query, a line in the definition of done, and re-read at review against the handler. Slice 3's R2 recurring, because the mitigation is a reading rather than a test.
R3 A client authors an assistant message. Harmless against an echo; prompt injection from Slice 5 on. role is server-assigned and the body is .strict(). AC-11 posts { role: "assistant", … } specifically and asserts the 400.
R4 Largest slice so far — two routes, six vendored blocks, a view, four components, a store, plus app-shell and dashboard changes. Something gets skimmed. Build order puts the boundary first: schemas → routes → rules → client → UI, so the security-relevant half is reviewable before a component exists. The vendored blocks are diffed against upstream, not read.
R5 The POST contract is rewritten in Slice 5, so a reviewer reads a shape that is about to change. Recorded as D6, with exactly what moves and what stays. The frontend's append model is chosen because streaming needs it, so that half does not change.
R6 Appending the response deviates from Slice 3's refetch rule and reads as an inconsistency. Argued in D12 rather than left to be found: a server-ordered list can be reordered by a mutation, an append-only transcript cannot. Neither uses onSnapshot, which is what the rule actually forbids.
R7 PRODUCT_SPEC.md F6.2 mentions “streaming assistant status”, which this slice does not build. Deliberate and stated: there is no stream to have a status for. F6.5 and the streaming half of F6.2 are Slice 5's, which the plan's conformance ledger already assigns them to.
R8 The breakpoint swaps component trees, so panel-local state is destroyed by a window resize. The draft moves to the store now, asserted by AC-25 — before Slice 5 has streaming state with the same exposure.
