Slice 03 · Projects · design companion

The path is the proof

Slice 2b closed the “trust a uid from the body” trap by making another user’s id impossible to write down: the profile route is the literal /users/me. Projects cannot do that — a project route needs an id. This is the slice that decides what replaces the trick, and the answer is that the document’s address carries the owner.

01 The boundary

Five routes and one wall. The browser holds no Firestore SDK at all, and firestore.rules denies the collection to every client — so the routes are not the convenient path to the data, they are the only path.

02 The hazard this slice exists to get right

Every route here takes a document id from the caller. There are two ways to make sure that id belongs to them, and they are not equally safe — one is a line of code that has to be present, the other is a property of where the document lives.

03 Create, and what makes the list current again

Two round trips per mutation, on purpose. CLAUDE.md rules out onSnapshot, so liveness is a refetch — and a refetch is also the only thing that reproduces the server’s updatedAt ordering without re-deriving it in the browser.

04 One request, every exit

Where a call to PATCH /api/projects/:projectId can end, and what the person at the keyboard is looking at when it does.

05 The five contracts

All mounted on the existing api function at both / and /api, all behind withVerifiedUser. Mutations are attested; plain authenticated reads are not — one rule for the whole API, unchanged since Slice 2.

Where the spec and the architecture disagree

PRODUCT_SPEC.md F2.2 asks for “strict per-user scoping via Firestore security rules.” It predates the API-only decision of 2026-08-17, and where the two disagree the architecture decision wins — so the rules block for this collection is allow read, write: if false and the scoping lives in the routes.

What F2.2 actually wants is delivered more strongly, not less: the browser cannot reach the collection at all, so there is no rule expression to get subtly wrong. Recorded as D2 in the PRD so a reviewer reading the spec alone does not read the denial as a regression.

06 Where the risk is tested

Thirty-four acceptance criteria. Which level each is proven at is a statement about where this slice thinks it can go wrong — and it is heavily weighted to L4, because the thing that would hurt is a route, not a component.

07 Risks carried into the build

#RiskMitigation
R1 A route that authenticates the caller and then trusts an id it was handed. The named trap of the API-only architecture, and this is the first slice whose routes take an id at all. Structural, per §02: the path is users/{token uid}/projects/{id}, so there is no comparison anywhere to review. AC-12 and AC-13 assert it from the wire.
R2 The composite index is missing in production and no test at any level can see it — the emulator serves any query, so L3, L4 and L5 all pass without one. It fails on the dashboard’s first load after deploy. Declared in firestore.indexes.json in the same commit as the query, in the definition of done, and re-read against the handler at review.
R3 A create that omits deletedAt makes a project invisible to its own list, because == null does not match an absent field. AC-1 asserts the stored value, not only the response body. Drawn at step 7 of §03.
R4 The slice is the largest so far and quietly grows a workspace screen, a restore surface, or pagination. Each is a numbered out-of-scope row with its owning slice. Rows are deliberately not navigable — the moment one becomes a link, Slice 4 has started.
R5 F2.2 asks for enforcement in security rules, which this slice deliberately does not do; a reviewer reading the spec alone reads the denial as a regression. Recorded as D2 and restated in the rules comment. See the callout in §05.
R6 Five routes and three components in one PR means the review is long enough that something gets skimmed. Build order puts the boundary first — schemas, routes, rules — so the security-relevant half is reviewable before any component exists.
R7 Refetching after every mutation is two round trips and reads as wasteful. It is CLAUDE.md’s stated liveness rule; the alternative is re-deriving the server’s updatedAt ordering in the browser. Named so it is judged as a decision rather than found as an oversight.
