The HighLevel Handshake

Four mechanisms this slice turns on, drawn rather than described: where the trust boundary falls, what actually protects an unauthenticated callback, why the token refresh has to be a transaction, and how five different failures all find their way back to one screen the user can act on.

Spec F1.2 · F1.3 Branch slice/02-highlevel-connection Depends on Slice 1 Date 2026-08-16

The boundary

Every design choice in this slice falls out of one constraint: the browser may never hold a HighLevel token. A token in the bundle is a token in the hands of anyone who opens devtools, and it would be scoped to a whole CRM location.

So the tokens live in a Firestore document that has no allow rule of any kind — denied to every client including its own owner — and the only code that reads it is the Admin SDK inside a Cloud Function. The connection status the dashboard renders is therefore not a Firestore read at all; it is an authenticated endpoint that returns a redacted projection.

The sequence

The callback is a public, unauthenticated endpoint — HighLevel redirects a browser to it and there is no session to read. So the question the whole flow has to answer is: whose connection is this? The state parameter is the only carrier, which makes it the one link back to a Firebase uid.

It is an encrypted token, not a stored one: { uid, exp } sealed with AES-256-GCM under a key derived from OAUTH_STATE_SECRET, valid for five minutes. Encrypted rather than merely signed because a signed payload is readable by whoever holds it — and this one travels in a URL to a third party, so the Firebase uid would otherwise sit in plain base64 in the user's history, in HighLevel's request logs, and in any Referer downstream. Decryption authenticates as well, so the GCM tag replaces a separate HMAC and tampering is caught before the plaintext is trusted.

This reverses an earlier decision — here's why

The state was going to be a single-use Firestore document, justified as replay protection. It doesn't buy that. A replayed callback carries an authorization code HighLevel has already consumed, so the exchange fails on its own. And the CSRF attack this parameter exists to stop — feeding a victim the attacker's code — is defeated by binding the uid into the state, not by consuming it: the connection simply lands on whichever uid the state names, which is the attacker's. So the collection cost a write on the hot path, a rules block, an L3 test and stale-document housekeeping, to provide protection two other mechanisms already gave. The reversal's price is one new secret, OAUTH_STATE_SECRET, which the state is sealed under.

The exact-match trap

redirect_uri must be one identical string in four places: the marketplace app's Redirect URL field, HL_REDIRECT_URI, the authorize URL at step 04, and the token exchange at step 07. A trailing slash in any one of them fails the exchange with an unhelpful error. It is read from a single env var everywhere, and AC-2 asserts it.

The rotation race

HighLevel's refresh tokens rotate on use: every refresh issues a new refresh token and invalidates the old one. Access tokens last about 24 hours, so this looks harmless right up until two requests find an expired token at the same moment — which is precisely what Slice 10's preview does when it fires several proxy calls on first render.

Both callers present the same refresh token. One wins. The other presents a token that has already been consumed and gets invalid_grant — and if that failure is persisted, the connection is dead until the user reinstalls the app. The fix is not a retry; it is making sure only one caller ever rotates.

The rule that follows from it

A failed refresh must never clear the stored refresh token. A network blip and a genuinely revoked grant look similar at the call site and are not remotely the same thing — so needsReconnect is set only on a definitive invalid_grant, and everything else leaves the record untouched.

Where failures land

The callback can end five ways and it renders none of them. It always answers with a 302 into the SPA, carrying an outcome — and every outcome converges on the same route, which refreshes connection state and hands off to a clean dashboard URL. Error copy then lives in exactly one place: the panel beside the button that retries it.

The surface

Four endpoints and one new route. Three endpoints are authenticated and check both that an ID token is present and that email_verified is true — Slice 1's D26, which exists because a router guard stops a browser and stops nobody calling the API directly. What gets tested

Forty-three acceptance criteria, every one of them observable. The distribution is worth reading as a design statement: the bulk sits at L4 because this slice is mostly Cloud Function behaviour against a stubbed HighLevel, and there is exactly one L5, covering the demo line. Dropping the state collection moved several assertions from L4 down to L1, where a decrypt-and-reject check belongs.

A few criteria are asserted twice on purpose — state rejection is unit-tested on the opener and integration-tested on the redirect it produces, because a correct opener wired to the wrong error code still ships a broken screen.

Before any code is written

The build's first task is walking the day-0 checklist against the sandbox and saving every response body into tests/fixtures/highlevel/. Hand-written fixtures encode our assumption about a response shape, so tests built on them pass while the real integration fails — and the checklist is also what proves the redirect URI matches and that the refresh token really does rotate.

  • Install into the sandbox location and confirm userType: "Location" with a locationId present.
  • Exchange a code — form-urlencoded, no Version header — and save the body.
  • Refresh once, confirm the new refresh token differs, then re-send the old one and confirm it now fails.
  • Read GET /locations/{id} for the name the connected state renders.
