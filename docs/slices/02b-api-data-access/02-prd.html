One door

The browser had two ways to reach the database. This slice removes one of them, and the interesting part is not the route it adds — it is the shape of the route, chosen so that the mistake this slice exists to prevent has nowhere to happen.

Spec F9.4 Branch slice/02b-api-data-access Depends on Slice 2 Date 2026-08-17

The acceptance criteria, the decisions and the test matrix live in 02-prd.md, which is the contract the build is graded against. This page carries only the four things that are faster to see than to read: the boundary that moves, the trap the route shape closes, where a failed profile fetch lands, and where the slice's risk sits across the five test levels.

The boundary, before and after

Slice 1 let the browser write users/{uid} directly, with Firestore rules as the enforcement. Slice 2 kept hlConnections/{uid} unreachable from any client and put a Cloud Function in front of it. Both patterns are defensible; carrying both is not, because the rules file then has to be read twice — once as enforcement, once as backstop — and nothing in it says which block is which.

The trap, and why the path closes it

IMPLEMENTATION_PLAN.md names the hazard for this slice exactly: a route that authenticates the caller and then trusts a uid from the request body. The usual defence is an equality check between the token's uid and the one in the request. It works, and it is one forgotten line — or one copy-paste into the next route — away from a cross-tenant write. So the defence here is not a check. It is a request shape with nowhere to put the second uid.

Where a failed profile fetch lands

Slice 1 swallowed profile failures on purpose: a profile is a convenience, not a precondition for having a session, and refusing entry over a failed write would trade a real capability for a cosmetic one. That half stands. What changes is that there is now a card whose job is to say so — every exit below ends somewhere a person can read, and none of them ends in a lost session.

The two endpoints

GET/api/users/me

The read the account card renders.

200{ profile } — email, displayName, ISO-8601 createdAt and updatedAt
200{ profile: null } — no document yet, or one that fails to parse
401unauthenticated — missing, malformed or expired ID token
403email_unverified — valid token, unverified address
ID token email_verified App Check — not required
PUT/api/users/me

Idempotent ensure — create if absent, touch if present.

200{ profile } — createdAt set once and never rewritten, updatedAt advanced
400invalid_body — any key outside { displayName?: string | null }, wrong type, or over 80 characters
401unauthenticated
403email_unverified
ID token email_verified App Check zod .strict()

One rule across the whole API, inherited from Slice 2: mutations are attested, plain authenticated reads are not. App Check buys nothing against a caller who already holds a valid ID token, and adding it to a read that runs on every dashboard visit would cost a reCAPTCHA round trip for no gain.

Where the risk sits

Twenty-eight acceptance criteria, and their distribution is itself a design statement. Eleven of them are L4 — the routes, exercised end to end against the emulators — because that is where a mistake in this slice leaks another tenant's data. The five L3 rules tests are all denials, which is what the backstop looks like when the enforcement has moved.

Risks

#RiskMitigation
R1 A route that authenticates the caller and then trusts a uid from the request. Structural, not procedural — /me gives the request nowhere to put one, and .strict() rejects a body that tries. Asserted by AC-8 and AC-10.
R2 The rules rewrite loosens something while deleting now-dead helpers. The L3 suite is rewritten in the same commit and every case is a denial; AC-15 and AC-16 re-assert the collections that were not the subject of the change.
R3 dist still carries the Firestore SDK through a transitive import. Measured before the PRD was written: the marker is present today and contributed by lib/firebase.ts alone. If it survives the build stage, the fix belongs in this slice.
R4 Extracting apiClient out of hlApi regresses Slice 2's connection panel. The extraction is verbatim and hlApi.spec.ts is not modified — an unchanged suite over refactored code is the assertion (AC-23).
R5 The account card is new UI in a slice whose demo line is “the app behaves exactly as before”. It is the minimum that makes the slice vertical: without a visible read path, the only proof of GET /api/users/me is an L4 test. Scope is capped at render-only — nothing in this slice writes displayName.
R6 Removing the frontend's database environment variables breaks a path that still reads them. All five references located during discovery and named in the PRD's in-scope list; AC-27 asserts a boot with neither variable set.
