Snapshots & restore

Every generation overwrites the project's files in place. This slice stores a point-in-time copy of the whole file set on the same commit, lists the copies in a sheet, and puts any one of them back — exactly, including deleting what came after.

F5.2 · F5.3 · F6.6 depends on Slice 6 mode: fast now — the project's files past — a stored copy restore — the one way back refused / deleted

The acceptance criteria, the decisions table and the test matrix live in 02-prd.md, which is the contract the build is graded against. This page draws the four things prose makes a reader assemble in their head.

1

What a snapshot copies

The whole slice turns on this. A generation rewrites some files and leaves the rest — Slice 6's D18 — so the copy that is easy to write is a copy of part of an app, and the failure only shows up later, in a restore that looks like it worked.

2

One batch, one commit

The assistant message says [file: index.html], the file document says what index.html contains, and the snapshot claims to be a copy of that moment. All three are one turn or the history describes a state that never existed.

3

Restore, step by step

Restore is the only operation in the product that deletes a file document, and the only one that can destroy a manual edit. Both facts are visible in the order of its steps.

4

The boundary

Two new collections, and the nested one is the easy miss: rules do not cascade, so a block on snapshots/{snapshotId} says nothing about the documents that hold the actual code.

5

Contracts

Two routes, neither naming a user. A resource id in a path is fine — it is checked for ownership and never trusted for identity.

6

Where the risk sits

Thirty-two acceptance criteria. Their distribution is a design statement: this slice's risk is in what actually reaches Firestore, so most of it is proven against the emulators rather than against a mock.

L2 component 3
L3 rules 2

L5 e2e 1

The pure half — the resulting-set merge, the next seq, the prune plan, the set-equality check — is deliberately large, because each of those is a decision that would otherwise live as an expression inside a handler where it cannot be asserted.

# Risk Mitigation
R1 Snapshotting the turn's writes rather than the project's set — smaller code, passes any single-generation test. D1 as a pure function with its own tests (AC-1); AC-7 asserts the untouched file over the wire.
R2 Files inline in one document: 20 × 100,000 > 1,048,576, so it fails only on the projects with the most code. D3's subcollection, with the arithmetic in the decision so a reviewer cannot simplify it back by accident.
R3 A restore that does not delete leaves a hybrid of two versions, invisible in the tree. D7; AC-12 asserts the negative, and __alt_files exists so the negative can be asserted at all.
R4 Unbounded growth — the safety snapshot means exploring history multiplies storage. D6's cap and prune in the same batch; AC-10 asserts the pruned snapshot's file documents are gone too.
R5 Committing the snapshot separately — one line shorter, and it opens a crash window. D4 keeps one batch owner; AC-9 asserts it against a recording batch rather than a reviewer's attention.
R7 Two writers for one file document again: a restore landing mid-generation would silently undo itself. D18 — disabled for the length of a stream, re-checked in the store because a keyboard path skips the button.
R8 The nested rules block forgotten: one block reads like coverage, and the code lives one level below it. D15 names both; AC-20 tests both; the definition of done asks for both by name.
R9 npx shadcn-vue add sheet needs the network, which an unattended session may not have. Vendor from the pinned upstream source with the deviation comment §7.2 requires, and say so in the build log.

R6 (a missing composite index — this project's recurring production-only failure) and R10 (the appendAssistantMessage signature change) and R11 (the extra read) are in 02-prd.md; they are argued rather than drawn, which is the right medium for each.
