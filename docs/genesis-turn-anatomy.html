Genesis · architecture walkthrough · one generation, end to end

Anatomy of a turn

A user types a sentence and an application appears. Between those two moments there are four processes, twenty steps, three stream layers and exactly one database commit. This traces the path a prompt actually takes through the code that exists today — and then runs it a second time, because the second prompt is a different problem from the first.

Browser Vue 3 SPA · Pinia workspace store · Monaco · sandboxed preview iframe
generate Cloud Function v2, asia-south1 · its own function, 540 s timeout, 512 MiB
Firestore named database hl-genesis · projects · messages · files · snapshots
Anthropic claude-opus-5 · messages.stream() · max_tokens: 64000

01 — The map

Four processes and two rewrites

The browser never talks to Firestore and never talks to Anthropic. Both are reached only through Cloud Functions, and the browser reaches those through same-origin Hosting rewrites — so there is no CORS preflight on the hot path and no second hostname in the app.

02 — The first turn

Twenty steps, one commit

The user has an empty project open. They type “build a contact dashboard with search and a list of upcoming appointments” and press send.

  1. Browser

    The composer hands off to the store.

    send() trims the draft, refuses if a stream is already open or a restore is running — the store is the boundary a keyboard shortcut cannot go around — draws an optimistic user bubble under a sentinel id, clears the draft, and calls runGeneration({ content }).

  2. Browser

    One fetch, not an EventSource.

    EventSource cannot POST and cannot set headers, so it could carry neither the ID token nor the App Check token, and its automatic reconnect would silently start a second paid generation. Instead: fetch with a ReadableStream body, an AbortSignal the store owns, and the frames parsed by our own incremental SSE parser.

  3. generate

    Attested, authenticated, parsed.

    App Check, then the Firebase ID token, then email_verified. The uid comes from the verified token and nowhere else — no route in this product names a user. Then Zod: { projectId, content } or { projectId, retry: true }, exactly one of them.

  4. Firestore

    The project, then the transcript, then the cap.

    A missing, soft-deleted or unreadable project all collapse into one 404. The transcript comes back oldest-first, capped at 200. A new turn needs room for two documents and a retry for one, so the cap is checked before a token is bought.

  5. Firestore

    The prompt is written down before the expensive half begins.

    This is why the prompt travels in the body of the streaming request rather than through a separate route. A turn that took two requests could fail between them — the message lands, the client dies, and the transcript keeps a prompt no reply is ever coming for. Writing it here buys the same durability with no window.

  6. generate

    The transcript becomes a context, in three steps that must run in order.

    Drop trailing assistant turns — a trailing assistant message is a prefill, and prefill is a 400 on this model, which is exactly what Retry after an interruption produces every time. Trim from the oldest end to 80,000 characters, keeping the newest turn whole whatever the budget says. Drop leading assistant turns, because the API requires the first message to be user.

  7. Firestore

    The project's files, with their content.

    On the first turn this is empty. On every turn after it, this read is what makes the model able to change an app rather than replace it — see §04.

  8. generate

    The request is assembled.

    claude-opus-5, max_tokens: 64000, effort: high, and a three-block system prompt: who the model is, how it writes files, and the HighLevel API cheat-sheet. The cheat-sheet is last and carries the cache_control breakpoint, so the stable prefix is a cache read rather than a re-send. The project's files go in after that breakpoint, because volatile content above it would invalidate the whole cached prefix.

  9. Anthropic

    The stream is opened — still before the flush.

    A missing API key, a refused request, a bad parameter: all of them are still ordinary JSON errors with a real status line at this point. One second later they would not be.

The flush — the one architectural boundary in this handler

res.flushHeaders() spends the status line. Everything above answers with a real HTTP status; everything below can only write an error frame onto a 200 that has already gone out. The handler's ordering is that rule executed, and the error handler is the same rule from the catch side.

  1. generate

    Headers, then a comment, then the stored prompt.

    Cache-Control: no-cache, no-transform and X-Accel-Buffering: no against intermediaries that buffer. Connection is deliberately not set — it is hop-by-hop, and with keep-alive on it the second prompt of every conversation comes back as an empty 400 over the reused socket. A keep-alive comment goes out immediately so the browser knows the request was accepted before the model has thought of anything.

  2. generate

    Three layers turn SDK events into frames.

    The mapper drops thinking deltas, tracks usage, enforces an 800 KB output cap and maps every ending to exactly one terminal event. The collector splits the reply into prose and files as it streams. The handler frames the result as SSE. Nothing above the collector knows the file-tag grammar exists.

  3. Browser

    The store routes each frame to a different surface.

    token grows the chat bubble. file_start puts a row in the tree and — only into an empty panel — opens the tab. file_chunk appends to a buffer keyed by the frame's own path, so interleaved files cannot bleed into each other. Monaco applies each chunk as an append edit, never setValue: the naive version resets the undo stack, snaps the viewport to line 1 and re-tokenises the whole file on every chunk.

  4. generate

    The terminal: one code path for success and interruption.

    The collector's end-of-input flush runs first, because a delimiter may end at end of input as well as at a newline. The op set is then validated whole — path shape, duplicates, the 100 KB byte cap, the 20-file union cap — and refused whole if any of it fails, because a generated app is a set of files that reference each other and writing two of three is broken in a way the user cannot see.

  5. Firestore

    One batch. One commit.

    The assistant message, every file write, the snapshot document, its file subcollection and any pruned version all stage on the same WriteBatch — worst case 63 writes, well inside Firestore's 500. Two commits would leave a crash window in which the transcript says [file: index.html] and no such file exists.

  6. Browser

    done, and then the refetch.

    The bubble is replaced by the server's message document, not the client's accumulated text. Then the file list is refetched, every open tab is re-read, and a revision counter ticks — which is what rebuilds the preview. The refetch is load-bearing rather than lazy: the server normalises content and computes size and both timestamps, so the bytes the browser watched arrive are not necessarily the bytes that were stored.

03 — The split

One reply, two destinations

The model writes a single stream of text. Some of it is a sentence to the user and some of it is an application — and the boundary between them is decided line by line, as the bytes arrive, rather than by a second parse at the end. 

what the model writes

I'll build a dashboard that lists your contacts with a search box,
and shows the next seven days of appointments beside it.

<genesis:file path="index.html">
<!doctype html>
<div id="contacts"></div>
</genesis:file>

…and what comes out of the collector

token       "I'll build a dashboard that lists…"
file_start  { path: "index.html" }
token       "[file: index.html]\n"      ← the marker, into the transcript
file_chunk  { path: "index.html", text: "<!doctype html>\n" }
file_end    { path: "index.html" }
The bug this shape exists to prevent

SDK deltas have nothing to do with line boundaries. <genesis:fi followed by le path="a.js"> is an ordinary pair of deltas, and a parser that scans each delta on its own leaks the first half into the chat bubble and never opens the file — while passing every test written by hand, because a hand-written test chunks on whole tags.

The same hazard exists one layer up, on the browser side: a chunk from a ReadableStream can end in the middle of event: to / ken. Both parsers are therefore driven split at every offset in their tests, which is how a real bug in the file splitter was found.

04 — The second turn

“Now add a dark theme”

Every one of the twenty steps runs again, unchanged. Three things are different, and together they are the whole of how Genesis modifies an app instead of replacing it.

The transcript is no longer empty

Step 4 now returns turn one's user and assistant documents, so step 6 sends a real conversation. What it does not send is the code: the assistant document holds the prose and a [file: index.html] marker line, never the file's contents. The transcript is a record of what was said, not of what was built.

The project state block appears

Step 7 now returns three files, and step 8 renders them into a second system block — the current content of every file, whole. Without it the model is shown a conversation describing files it cannot see, so it writes them again from the description. This block is the single thing that makes “add a search box” an edit rather than a rewrite.

Four properties in it are load-bearing. Whole files or no file — handed half a file the model completes it from imagination and writes the whole thing back, silently replacing code the user never mentioned. A skipped file is still named in a manifest, because a model that cannot see app.js concludes there is no app.js and creates a second one under another name. Its own budget — 120,000 characters, separate from the transcript's 80,000 — so a long conversation can never evict the code. And it is appended after the cache_control breakpoint, so it never invalidates the cached prefix above it.

The writes are rewrites

A path the project already holds is written with merge: true, so createdAt — the date the file was first generated — survives. A generation creates and updates and never deletes; restoring a snapshot is the only operation in the product that removes a file document, which is precisely what that restraint was kept for.

Which is exactly where Slice 14 begins

A follow-up turn can already choose which files to rewrite. It cannot choose which lines — so “add one more theme” re-emits eight kilobytes to change forty lines, at output rates, generated serially. Slice 14 adds a located change to the grammar and moves the project-state block past the transcript so the conversation becomes cacheable. The design companion for it works through the arithmetic.

05 — When it goes wrong

Two failure channels, decided by one line of code

Everything hinges on whether res.flushHeaders() has run. Before it, a failure is an HTTP status the client can act on. After it, a 200 is already in flight and the only honest thing left is a frame the client can parse.

What went wrong Channel What the browser does What survives
Project missing or soft-deleted 404 before the flush Rolls the optimistic bubble back, restores the draft into the composer Nothing was stored — the prompt is written after this check
Transcript at its 200-message cap 409 before the flush Same rollback; no Retry offered, since retrying would fail again Nothing was stored
Model refuses the request error frame · refused Appends the server's persisted message and shows the reason The prompt, and a failed assistant turn with its reason
Upstream drops mid-stream error frame · upstream Keeps what streamed, marks it interrupted, offers Retry The partial reply, flagged truncated. Files are refused whole
Connection lost after the flush read throws Keeps the bubble, offers Retry — the request may have reached the server Whatever the server committed; the transcript reconciles on the way back in
The user closes the tab res.on('close') — The model stream is aborted so it stops billing; the partial and its files are still committed, because they belong to the project rather than to the connection
A bad path, a duplicate, an oversized file, an unterminated block done, with fileError Shows the reason; the tree does not move The message commits; no file is written — the op set is refused whole

The listener that catches a departing user is on the response, not the request: express.json() has already drained the request body by the time the handler runs, so req emitted its close long ago and the disconnect would never be observed.

06 — In short

Five properties worth carrying in your head

  1. The prompt is durable before the expensive half starts. One request per turn, and the user message is committed before the model stream is opened.
  2. The flush is the boundary. Everything decidable cheaply is decided above it, where a real status code is still available.
  3. The reply is split as it streams, so file boundaries are live and the streamed bytes equal the stored bytes by construction.
  4. A turn commits once. Message, files, snapshot and prune share one batch, so the transcript can never describe a file that does not exist.
  5. The second turn differs from the first only by what it is shown. The transcript carries what was said; the project-state block carries what was built. Take that block away and every follow-up prompt starts a new app.
